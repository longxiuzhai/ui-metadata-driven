# 架构说明

## 1. 系统定位

项目采用“前端页面容器 + 后端卡片编排”的方式。后端只返回受控元数据，前端只解释预先注册的能力。目标是让业务模块可以独立贡献卡片和动作，同时保持组件体验、安全边界和协议演进可控。

当前实现粒度是卡片，不是任意组件树。复杂交互通过已注册 Vue 组件或表单扩展。

## 2. 模块边界

| 模块 | 核心职责 | 不应包含 |
|---|---|---|
| `card-platform` | Card/Action 模型、SPI、注册器、条件、校验、页面装配 | 具体客户业务、Web Controller、租户数据 |
| `tenant-customization` | 业务 Provider、数据接口、Action Handler、演示仓库 | 对 `application` 的反向依赖 |
| `application` | 启动入口、统一元数据/动作 API、账号上下文、异常映射、集成测试 | 可复用业务卡片实现 |
| `frontend` | 页面容器、组件、表单、路由、动作运行时和白名单 | 执行后端下发代码、把按钮隐藏当真实鉴权 |

定制模块通过 `META-INF/spring.factories` 暴露 `DemoTenantAutoConfiguration`，再由组件扫描注册 Provider、Controller 和 Handler。`application` 通过 Maven 依赖选择是否装入该定制模块。

这里的 SPI 是 Spring Bean 扩展点，不是 JDK `ServiceLoader`，也不支持运行时热装卸 JAR。

## 3. 页面装配链路

```text
浏览器请求统一元数据 API
  → JWT Filter 校验 Token，并从 MySQL 加载账号角色和权限
  → CardRequestContextFactory 构造可信账号上下文
  → CardProviderRegistry 按 pageCode 取得 Provider
  → @ConditionalOnProperty 在启动期决定 Bean 是否存在
  → @CardConditional 在请求期过滤租户/权限/Feature
  → provider.supports(context) 执行业务特有轻量判断
  → provider.definition(context) 生成 CardDefinition
  → CardDefinitionValidator 执行白名单和安全校验
  → 按 order、code 排序，并按权限过滤卡片动作
  → 返回 CardPageDefinition
```

启动期注册器还会检查同一 `pageCode` 下的 `cardCode` 冲突。Provider 声明的 `cardCode()` 必须与 Definition 中的 code 一致。

## 4. 前端渲染链路

```text
App.vue 根据路由建立 pageCode 和 pageContext
  → api.ts 请求 CardPageDefinition
  → v-for 创建 DynamicCard
  → cardRegistry 将 component 编码映射为本地 Vue 组件
  → DynamicCard 替换 dataApi 中的页面上下文占位符
  → 卡片独立加载、取消请求、显示骨架/空态/错误态
  → 组件只接收 data 和经过校验的 props
```

当前组件白名单：`KeyValueCard`、`TagGroupCard`、`TimelineCard`。未知组件由前端 `UnknownCard` 降级展示，但正常情况下会先被后端校验器拒绝。

`loadStrategy` 支持 `eager` 和 `on-visible`。每张卡片是独立失败边界，不应因为一个数据接口失败而使整页不可用。

## 5. 动作链路

动作元数据只描述意图：

- `refresh`：刷新当前卡片；
- `navigate`：通过 `routeRegistry` 跳转命名路由；
- `open-form`：通过 `formRegistry` 打开本地表单，并调用后端动作。

```text
DynamicCard 发出 action 事件
  → ActionRuntime 解析 page-context/card-data/account/literal 参数
  → refresh | routeRegistry | formRegistry
  → POST prepare 获取初始值和版本
  → POST execute 提交 values/version/requestId
  → UiActionHandlerRegistry 查找 Handler
  → 权限和 supports 再校验
  → Handler 执行业务修改
  → 返回消息和待刷新 cardCode
```

路由、表单、组件、动作类型和后端命令都使用稳定编码，不允许元数据直接指定任意 URL 或提交地址。

## 6. 条件模型

| 层次 | 执行时机 | 适合处理 |
|---|---|---|
| Spring Boot Condition | 应用启动 | 模块/JAR 是否存在、配置开关 |
| `@CardConditional` | 每次元数据请求 | 权限、租户、Feature Flag |
| `supports(context)` | 每次元数据请求 | Provider 特有且轻量的业务条件 |

避免在 `supports` 中访问数据库或远程服务，否则一个页面的多个 Provider 会放大请求成本。复杂状态应批量加入上下文，或由卡片数据 API 决定返回内容。

## 7. 协议与白名单

后端 `CardDefinitionValidator` 当前校验：

- 组件编码和加载策略；
- 1–24 的响应式栅格跨度；
- 站内 `/api/` 数据地址；
- `refresh/navigate/open-form` 动作类型；
- 参数来源、字段路径和原型链危险字段；
- 表单展示方式及动作必填目标。

新增协议能力时应同时修改 Java 模型、校验器、TypeScript 类型、前端运行时、测试和 API 文档。不要仅放宽校验器而没有对应的执行语义。

## 8. 安全边界

- 卡片和按钮可见性只改善体验，不能替代后端鉴权；
- 每个卡片数据 API 必须重新校验账号权限和实体数据权限；
- 每个 `UiActionHandler` 必须重新校验权限、上下文和输入字段；
- 不信任客户端传来的租户、用户、权限、版本号和业务参数；
- 客户域查询通过 `CurrentTenantProvider` 从登录主体解析租户，只有测试/演示免登录模式回退到 `demo`；
- 不接受外部 `dataApi`、任意路由 URL、任意表单组件或脚本表达式；
- 修改动作需要并发控制、幂等和审计。

生产配置禁止 `X-*` 请求头覆盖账号权限；该能力只在自动化测试配置中开启。

## 9. 生产化边界

接入真实系统前至少需要：

- 将 JWT 密钥放入密钥管理系统，并补充 Token 撤销和登录风控；
- 在数据接口和 Handler 中实现实体级数据权限；
- 客户、标签、轨迹、订单、会员及客户版本已持久化；继续持久化动作幂等记录和审计日志；
- 为元数据和数据接口增加超时、指标、追踪和告警；
- 定义协议向后兼容策略和前端支持版本；
- 对参数大小、字符串长度、对象深度和请求频率设限；
- 增加组件契约测试、端到端测试和模块移除测试；
- 明确多租户隔离和配置发布流程。
