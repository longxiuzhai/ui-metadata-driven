# 扩展卡片开发指南

## 1. 后端只分三部分

| 模块 | 职责 |
|---|---|
| `application` | 核心应用：统一元数据接口、账号身份、权限与 Feature 上下文、应用启动 |
| `card-platform` | 通用 Card：模型、Provider SPI、Condition、校验和装配器，不包含具体页面业务 |
| `tenant-customization` | 租户定制：客户详情、首页等具体 Provider 和卡片数据接口 |

依赖方向保持单向：

```text
card-platform ← tenant-customization
      ↑                 ↑
      └──── application ┘
```

`card-platform` 不知道有哪些页面或租户；`tenant-customization` 不依赖核心应用；核心应用通过 `CardProviderRegistry` 发现所有 `CardProvider`，按页面建立索引，并在启动时校验重复编码。

三层是代码归属边界，不是可插拔能力的最小粒度。每张卡片仍然是独立 Provider，具有三层条件：

1. `@ConditionalOnProperty`：启动期启停单个卡片能力；
2. `@CardConditional`：请求期按租户、权限和 Feature 过滤；
3. `supports(context)`：Provider 自己的轻量业务判断。

例如 `--metadata.cards.behavior-trace.enabled=false` 只移除行为轨迹 Provider，不影响客户详情页的其他卡片。

## 2. 统一接口

所有页面使用同一个接口：

```http
GET /api/ui/pages/{pageCode}/cards
```

例如：

```http
GET /api/ui/pages/customer_detail/cards?customerId=1001
GET /api/ui/pages/home/cards
```

旧地址 `/api/ui/customer-detail/cards` 和 `/api/ui/home/cards` 不再保留；所有调用和测试统一使用 `/api/ui/pages/{pageCode}/cards`。

核心应用从当前账号加载租户、权限和 Feature，再构造统一的 `CardRequestContext`。演示环境允许使用 `X-Tenant-Id`、`X-User-Id`、`X-Permissions` 和 `X-Features` 请求头覆盖账号信息。

页面元数据只决定“显示什么”；每张卡片的 `dataApi` 仍需在真实项目中执行数据级鉴权。

## 3. 工作原理

```text
账号与统一请求入口（application）
  → 构造 CardRequestContext
  → CardPageAssembler 按 pageCode、权限、租户和 Feature 过滤
  → 返回当前用户可见的卡片清单
          ↓
Vue 页面容器
  → 根据 component 从 cardRegistry 选择组件
  → 每张卡片独立请求 dataApi 并渲染
```

租户定制 JAR 中的 Provider 与数据接口通过 Spring Boot AutoConfiguration 注册。移除该 JAR 后，定制卡片和接口会一起消失，核心应用和前端容器无需修改。

## 4. 最小示例：客户备注卡片

在 `tenant-customization` 中增加 Provider，并复用前端已有的 `KeyValueCard`：

```java
@Component
@CardConditional(permissions = "customer:note:read")
public class CustomerNoteCardProvider implements CardProvider {
    @Override
    public String pageCode() {
        return "customer_detail";
    }

    @Override
    public String cardCode() {
        return "customer_note";
    }

    @Override
    public CardDefinition definition(CardRequestContext context) {
        return new CardDefinition(
            cardCode(), "客户备注", "KeyValueCard", 30,
            new ResponsiveSpan(24, 12, 12),
            "/api/customers/{customerId}/note", "eager",
            "customer:note:read",
            Map.of("columns", 1, "fields", List.of(
                Map.of("key", "content", "label", "备注")
            )),
            List.of()
        );
    }
}
```

Provider 只描述卡片，不读取卡片数据。数据接口仍由定制模块提供：

```java
@RestController
public class CustomerNoteController {
    @GetMapping("/api/customers/{customerId}/note")
    public Map<String, String> note(@PathVariable String customerId) {
        // 实际项目中先校验当前账号对 customerId 的数据权限。
        return Map.of("content", "下周再次联系客户");
    }
}
```

## 5. Condition 如何选择

| 机制 | 用途 | 例子 |
|---|---|---|
| Spring Boot Condition | 启动时决定 Provider 是否注册 | 模块开关、依赖是否存在 |
| `@CardConditional` | 请求时执行通用过滤 | 权限、租户、Feature Flag |
| `supports(context)` | Provider 特有的轻量判断 | 只对某类客户展示 |

`supports` 不应执行 SQL 或远程请求。复杂状态应批量放入请求上下文，或者交给卡片数据接口处理。

## 6. 扩展边界

- 已有组件能表达需求时，只新增定制 Provider；
- 新交互形态需要先开发 Vue 组件并加入 `cardRegistry`；
- Provider 不得返回 HTML、JavaScript、CSS、外部组件地址或外部数据 URL；
- 元数据可见性不能替代数据接口鉴权；
- `cardCode` 只需在同一 `pageCode` 内唯一；
- 当前完整示例位于 `backend/tenant-customization`。

## 7. 联动检查清单

- 新 Provider：补充统一元数据接口测试，并覆盖权限或 Feature 过滤；
- 新组件编码：同时更新前端 `cardRegistry.ts` 和后端 `CardDefinitionValidator`；
- 新格式化器：更新 `frontend/src/formatters.ts` 并验证未知格式化器降级；
- 新页面：同步增加前端路由、页面上下文和元数据请求映射；
- 新数据 API：实现真实权限校验，不能依赖卡片已被元数据过滤；
- 完成后执行根目录 `mvn test`、前端 `npm test` 和 `npm run build`。
