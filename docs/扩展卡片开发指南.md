# 扩展卡片开发指南

## 1. 这套机制解决什么问题

客户详情页只负责提供统一布局，不写死具体业务卡片。每个业务模块以独立 JAR 提供自己的卡片描述和数据接口。

例如安装“客户备注插件”后，详情页自动出现“客户备注”卡片；移除该插件 JAR 后，卡片和对应接口一起消失，主应用和详情页代码都不需要修改。

这套机制只动态组合已有卡片类型，不允许后端下发 Vue、JavaScript 或远程组件。

## 2. 工作原理

```text
独立插件 JAR
  ├─ CardProvider：描述卡片标题、组件、数据地址和布局
  └─ Data API：返回卡片需要的业务数据
          ↓ Spring Boot 自动发现
卡片聚合服务
  → Condition 过滤模块、租户、权限和 Feature Flag
  → 校验并排序卡片定义
  → 返回当前用户可见的卡片清单
          ↓
Vue 详情页
  → 根据 component 从前端注册表选择组件
  → 每张卡片独立请求 dataApi 并渲染
```

一次页面展示实际包含两类请求：

1. 页面先请求 `/api/ui/customer-detail/cards`，获得需要展示哪些卡片；
2. 每张卡片再请求自己的 `dataApi`，获得业务数据。

元数据接口只决定“显示什么”，数据接口仍然必须执行真实鉴权。

## 3. 模块职责

| 模块 | 职责 |
|---|---|
| `card-platform` | 通用卡片模型、Condition 和安全校验，不包含客户业务 |
| `customer-detail-contract` | 客户详情 Provider SPI 和上下文，是插件的编译契约 |
| `customer-detail-feature` | 聚合所有 Provider，提供客户详情元数据接口 |
| 业务插件 JAR | 实现 Provider，并提供自己的业务数据接口 |
| `application` | 引入需要启用的插件并启动应用 |

依赖方向必须保持单向：

```text
业务插件 → customer-detail-contract → card-platform
主应用   → 业务插件
```

插件不能依赖主应用，也不能直接调用聚合服务。

## 4. 最小示例：客户备注卡片

下面新增一个只显示客户备注的卡片，并复用前端已有的 `KeyValueCard`。

### 4.1 实现 Provider

```java
@Component
@CardConditional(permissions = "customer:note:read")
public class CustomerNoteCardProvider
        implements CustomerDetailCardProvider {

    @Override
    public String cardCode() {
        return "customer_note";
    }

    @Override
    public CardDefinition definition(CustomerDetailContext context) {
        return new CardDefinition(
            "customer_note",
            "客户备注",
            "KeyValueCard",
            30,
            new ResponsiveSpan(24, 12, 12),
            "/api/customers/{customerId}/note",
            "eager",
            "customer:note:read",
            Map.of(
                "columns", 1,
                "fields", List.of(
                    Map.of("key", "content", "label", "备注")
                )
            ),
            List.of()
        );
    }
}
```

Provider 只描述卡片，不读取卡片数据。这里表达的是：使用 `KeyValueCard` 展示一个 `content` 字段，数据从指定接口加载。

### 4.2 提供数据接口

```java
@RestController
@RequestMapping("/api/customers")
public class CustomerNoteController {

    @GetMapping("/{customerId}/note")
    public Map<String, String> note(@PathVariable String customerId) {
        // 实际项目中需要在这里鉴权并查询数据库。
        return Map.of("content", "下周再次联系客户");
    }
}
```

最终卡片组件收到的数据为：

```json
{
  "content": "下周再次联系客户"
}
```

### 4.3 让 Spring Boot 发现插件

插件通过 AutoConfiguration 注册，不依赖主应用的包扫描：

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnClass(CustomerDetailCardProvider.class)
@ComponentScan(basePackageClasses = CustomerNoteCardProvider.class)
public class CustomerNotePluginAutoConfiguration {
}
```

Spring Boot 2.7 在插件的 `META-INF/spring.factories` 中登记：

```properties
org.springframework.boot.autoconfigure.EnableAutoConfiguration=\
com.example.plugin.note.CustomerNotePluginAutoConfiguration
```

最后在主应用中加入该插件的 Maven 依赖。启动后，聚合服务会自动发现 `CustomerNoteCardProvider`。因为使用的是前端已有组件，所以客户详情页不需要修改。

## 5. Condition 如何选择

| 机制 | 用途 | 例子 |
|---|---|---|
| Spring Boot Condition | 启动时决定 Provider 是否进入容器 | 模块开关、依赖类是否存在 |
| `@CardConditional` | 请求时执行通用过滤 | 权限、租户、Feature Flag |
| `supports(context)` | 请求时执行该 Provider 特有的简单判断 | 只对企业客户展示 |

`supports` 不应执行 SQL 或远程请求，否则每次加载页面都可能产生多个额外 I/O。复杂状态应提前批量放入上下文，或者由卡片数据接口处理。

## 6. 新增卡片时的判断

- 如果已有组件能表达需求，只新增后端插件；
- 如果需要新的交互形态，先开发 Vue 组件并加入 `cardRegistry`，再允许 Provider 引用；
- Provider 不得返回 JSON 字符串、HTML、JavaScript、CSS、外部组件地址或外部数据 URL；
- 卡片是否可见不能替代数据接口鉴权；
- `cardCode` 必须全局唯一，避免不同插件相互覆盖。
